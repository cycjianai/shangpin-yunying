# 美团买药/医疗器械商家版整店商品迁移

本分支专用于已授权的美团买药/医疗器械类商家版后台。它处理“从源门店完整备份，再把分类和商品复制到目标门店”的任务，不是超市/闪购调价流程。医疗器械商品还包含资质、器械属性、详情媒体和平台标品约束，不能只复制名称、价格和库存。

## 识别与边界

常见页面线索是 `yiyao.meituan.com/main/frame#/page/product/...`，例如商品列表、快捷建品和商品详情。开始前从页面可见门店名和当前接口响应同时确认：

- 当前登录的是源店还是目标店；
- 当前 `wmPoiId`、账号节点和商品接口门店 ID；
- 当前页面属于美团买药/医疗器械商家版，而不是超市/闪购后台；
- 本次授权是只备份、同步分类、试建若干商品，还是全量新增。

切换账号或门店后必须重新做身份预检。旧页面、旧 Cookie 健康标记或上一次任务保存的 `wmPoiId` 都不能替代当前证据。

## 迁移对象与身份账本

迁移以 SPU 为对象、SKU 为验真粒度。所有 ID 和条码按字符串保存。账本至少包含：

- 源/目标门店身份与证据时间；
- 源 SPU ID、目标 SPU ID、源/目标 SKU ID；
- UPC、源店内码、目标店内码、规格、价格、库存、单位；
- 平台末级类目及完整路径；
- 店内一级分类、二级分类及完整路径，源分类 ID 到目标分类 ID 的映射；
- 标品 ID、是否标品、标库查询结果和匹配证据；
- 主图、详情图、资质图及其他媒体的角色、顺序、源 URL、本地资产、内容哈希和目标 URL；
- 写前、提交、写后读回状态以及 `truth_source`。

商品名只能辅助人工识别，不能作为唯一主键。优先使用源 SPU/SKU、UPC 和明确的分类/规格组合；多 SKU 必须逐条映射，不能只拿第一条 SKU 代表整个 SPU。

## 第一阶段：源店全量归档

### 1. 冻结范围

记录任务 ID、源店身份、开始时间、商品状态范围和分页参数。全量迁移应覆盖在售、停售、缺货及页面定义的其他必要状态，不能只备份当前列表第一页或当前筛选结果。

### 2. 拉取列表与详情

先分页读取源店全部 SPU，去重后对每个 SPU 读取完整详情。详情必须保留平台原始结构，至少覆盖：

- `name`、`spTitle`、补充标题、描述和卖点；
- 平台类目、店内分类/标签、医疗器械属性及选中值；
- `picture`、`picContent`、`spPicContent`、`quaPictures`、注册/认证图片及视频字段；
- 每条 SKU 的规格、UPC、价格、库存、单位、店内码及平台 SKU ID；
- 标品关联、审核状态、销售状态和其他保存时需要的业务字段。

列表记录用于证明全量覆盖，详情记录用于重建商品。二者数量和 SPU ID 集合必须对账一致；详情缺失的 SPU 不能进入“完整备份”。

历史搜索线索包括商品列表 `searchListPageNew` 和页面详情读取能力，但端点、前端导出名与 payload 必须从当前成功请求重新确认。

### 3. 媒体离线化

从完整详情递归提取媒体，但同时保留明确角色与顺序。至少区分：

- 主图；
- 商品详情图；
- 平台标准详情图；
- 医疗器械资质图、注册/认证图；
- 营销图、UPC 图、票据图；
- 商品视频和标准视频。

每个唯一 URL 生成稳定资产 ID（可用 URL 的 SHA-256），下载到本地并记录字节数、内容 SHA-256、扩展名和状态。下载失败、404 或非媒体响应逐条记录，不能把“URL 已保存”当成“图片已备份”。同一资产被多个商品引用时只下载一次，但保留所有商品角色引用。

### 4. 归档完成门

只有同时满足以下条件才可通知用户切换目标账号：

- 列表 SPU 数等于归档 SPU 数，SPU ID 集合一致；
- 每个 SPU 都有完整详情；
- SKU 总数与详情汇总一致；
- 媒体清单中的每个成功资产都通过文件存在、字节数和内容哈希校验；
- 失败媒体有精确来源和原因；
- 归档 JSON、媒体清单、SKU 审计、全店商品清单和汇总相互对账；
- 导出物中没有 Cookie、Authorization、token、签名或其他登录秘密。

## 第二阶段：目标店分类复制

商品新增前先读取目标店现有分类，并用源店分类树建立差异。分类同步必须按父子顺序执行：

1. 创建或复用同名一级分类；
2. 在已确认的目标一级分类下创建或复用二级分类；
3. 保存 `source_category_id/path -> target_category_id/path` 映射；
4. 回读目标分类树，核对每条完整路径、父子关系、顺序和启用状态。

只创建一级分类不是完成。不能仅按二级分类名称全局匹配，因为不同一级分类下可能重名。“未分类”只在用户明确要求试建商品放入该分类时使用；全量迁移必须恢复源商品对应的完整店内分类路径。

## 第三阶段：目标店写前预检与样本

### 1. 只读预检

在目标店完成以下只读检查：

- 商品列表和详情读取可用；
- 分类树及映射可用；
- 标准商品库查询可用；
- 媒体上传或目标 CDN 复用路径可用；
- 当前页面动态签名、`mtgsig`、`csecversion` 等上下文健康；
- 用源候选查目标店，排除已经存在或处在“待优化”的重复商品。

医疗器械快捷建品页面曾观察到标准库查询路径片段 `reuse/health/product/shangou/sp/r/searchSpListByCond`，请求字段包含 `pageNum`、`pageSize`、`upcCode`、`name` 和当前 `wmPoiId`。这只是运行时发现线索；每次仍需从当前页面成功请求确认。

### 2. 一条与五条样本

先用一条商品走完“创建/引用 → 全字段覆盖 → 独立回读”，再用五条覆盖不同类型：单 SKU、多 SKU、有资质图、有详情图、需要标库查询。样本验收必须检查：

- 商品名称和平台类目；
- 一级、二级店内分类；
- 主图不是平台默认图，详情图和资质图来自备份资产；
- SKU 数量、规格、UPC、价格、库存、单位和店内码；
- 医疗器械必填属性与备份一致；
- 目标列表和目标详情均能独立读回。

样本未通过时只修复样本和迁移逻辑，不进入全量。

## 第四阶段：为每个商品选择建品路径

按下表明确分流，不能对所有商品调用同一个“新增”接口：

| 当前证据 | 动作 | 禁止动作 |
| --- | --- | --- |
| 目标店已经存在且身份唯一 | 读取目标完整详情并覆盖授权字段 | 重复建品 |
| 标准库按 UPC 返回唯一精确商品 | 引用该标品，取得目标 SPU/SKU 后再按允许字段覆盖销售和店内信息 | 只凭相似名称选择 |
| 标准库零匹配 | 标记 `catalog_not_found`；如用户另行授权，走“提报标品”并等待审核 | 把“仅可引用标库”解释为“库里已有商品” |
| 标准库多匹配或 UPC/规格冲突 | 标记 `catalog_ambiguous`，人工复核 | 猜一个最相似商品 |
| 当前类目允许自建 | 按当前页面的自建流程创建，再执行全字段覆盖 | 沿用旧超市 payload |
| 平台提示“其他商家提交审核” | 标记 `catalog_auditing`，记录可重试时间 | 高频重试或重复提报 |
| 目标商品为“待优化” | 进入目标店商品优化/编辑路径 | 再建一个重复商品 |

“提报标品”是向平台提交新的标准商品资料，会进入审核，不是直接引用；它需要单独授权，并按平台要求提交真实、可证明的商品信息和资质。

## 第五阶段：创建后全字段覆盖

创建或引用只负责取得目标对象，不代表迁移完成。随后重新读取目标完整商品，以目标对象为基底，只覆盖源店可迁移字段：

- 名称、补充标题、描述和卖点；
- 平台类目和目标店分类映射；
- 医疗器械属性和必填项；
- 主图、详情图、资质图及其顺序；
- 每条 SKU 的规格、UPC、价格、库存、单位和店内码；
- 用户明确要求复制的其他销售字段。

以下字段不得从源店硬拷贝到目标店：目标门店 ID、目标 SPU/SKU ID、账号 ID、审核流水、目标平台生成的应用码、目标店专属活动 ID，以及当前页面定义为只读或平台托管的字段。

如果保存是完整 SPU 提交，遵循 [meituan-product-editing.md](meituan-product-editing.md) 的单写者规则：每次保存前重读目标完整详情，同一 SPU 串行，跨 SPU 才允许受控并发。

### 媒体写入规则

媒体必须来自归档清单，不能接受建品时自动带入的默认美团图库作为复制结果。优先把本地已校验资产上传到目标页面当前的上传能力，记录上传返回的目标 URL 和源资产哈希；只有当前页面明确支持复用源美团 CDN URL 且回读可访问时，才允许直接复用。

写后按角色和顺序比较媒体。URL 可能因重新上传而变化，因此最终以源资产内容哈希、目标可访问性、角色和顺序验真。单个源媒体永久 404 时只省略该资产并标记 `partial_success/source_media_invalid`，不能把整件商品静默记为完全一致。

### 店内码与多规格

店内码属于 SKU，不属于 SPU。每条源 SKU 必须映射到唯一目标 SKU 后写入对应店内码；不得把第一条 SKU 的店内码复制到所有规格。店内码、UPC、规格和价格库存一起回读，以防完整 SPU 保存覆盖了相邻 SKU。

## 第六阶段：独立回读与一致性判定

写响应仅记为 `accepted`。丢弃提交对象，从目标店商品列表和详情重新读取，按目标 SPU/SKU ID 与 UPC 交叉验证。建议把验真拆为以下字段组：

- `identity`：目标 SPU、SKU 集合、UPC 和规格映射；
- `main`：名称、类目、描述等主档；
- `store_category`：完整一级/二级路径；
- `attributes`：医疗器械属性和必填值；
- `sales`：价格、库存、单位、售卖状态；
- `store_code`：每条 SKU 的店内码；
- `main_media`：主图角色、顺序、哈希和可访问性；
- `detail_media`：详情图角色、顺序、哈希和可访问性；
- `qualification_media`：资质/认证图角色、顺序、哈希和可访问性。

所有必需字段组通过才能标记 `exact_verified`。只验证名称、`main/detail/tags/sku` 的粗粒度布尔值不足以证明图片、店内码和资质已完整复制。

## 批量任务、并发和续跑

批量迁移使用持久化任务和追加式账本，不把未等待的浏览器 Promise 或临时交互会话当成后台 worker。任务至少保存 `queued/running/stopping/stopped/completed/failed`，商品结果至少保存 `pending/accepted/exact_verified/partial_success/failed/skipped/unknown`。

建议将读取、媒体、写入和回读分成独立受控池：

- 分类写入串行；
- 同一 SPU 写入串行；
- 浏览器强签或共享页面关键段串行；
- 媒体上传可与商品写入分池，但必须有界；
- 跨 SPU 从并发 1 开始，按 1 → 5 → 20 → 50 → 100 阶梯放量；
- 任一级出现身份错配、图片缺失、店内码错误、`unknown`、`403/429` 或人工挑战即停止新任务领取。

每个商品完成回读后立即写账本。恢复时重新验证目标店身份和当前商品状态，只处理尚未 `exact_verified` 的商品；写后超时先读回再决定是否重试，避免重复建品。

## 医疗器械迁移失败分类

保留平台 code 和原始中文消息，并映射到稳定原因：

| 证据示例 | 稳定原因 | 处置 |
| --- | --- | --- |
| `12004`、商品“待优化” | `platform_pending_optimize` | 转商品优化/编辑，不重复新增 |
| “当前类目仅可引用标库建品” | `platform_catalog_required` | 精确查标库；零匹配转 `catalog_not_found` |
| `3009`、其他商家已提交审核 | `platform_catalog_auditing` | 记录平台提示时间后再查询 |
| 类目仅允许一个规格 | `platform_single_sku_only` | 不擅自丢规格，需用户决定拆分或跳过 |
| UPC 类目与当前类目不同 | `platform_sku_category_conflict` | 停止并复核 UPC/类目 |
| 图片无效或源媒体 404 | `source_media_invalid` | 精确到资产处理，标记部分成功或失败 |
| 写响应成功但目标详情未物化 | `materialization_delay/unknown` | 有界等待并回读，不立即重写 |

业务拒绝、零标库匹配、多匹配和类目冲突都不自动重试。

## 迁移输出与完成门

下列字段是内部逐商品账本的最低证据，不是另一种用户交付表头；最终必须按
`references/core/output-contract.md` 映射到统一七表。内部账本建议为：

```text
source_spu_id,target_spu_id,source_sku_ids,target_sku_ids,upc,name,
build_route,store_category_path,result,platform_code,message,
identity,main,store_category,attributes,sales,store_code,
main_media,detail_media,qualification_media,truth_source,updated_at
```

只有同时满足以下条件才可宣布“整店复制完成”：

- 源店全量归档通过列表、详情、SKU 和媒体完成门；
- 目标一级、二级分类树逐路径回读一致；
- 所有可执行商品都有目标 SPU/SKU 身份；
- 每个成功商品的主档、属性、销售、店内码、主图、详情图和资质图均独立读回一致；
- 没有未处理的 `unknown`；
- 标库零匹配、审核中、待优化、单规格限制、类目冲突和媒体异常逐条保留；
- 汇总数等于逐商品状态之和，账本可停止续跑；
- 日志和交付物已脱敏。

平台规则导致无法复制的商品不能被“成功率”吞掉。报告应明确区分：完全一致、部分成功、审核中、需优化、标库不存在、平台规则阻断和其他失败。
