# 美团商品信息编辑与店内码修改

本分支用于已授权门店内的商品名称、规格、条码、店内码和其他属性编辑。商品编辑常是“完整 SPU 保存”，不是单 SKU 字段 patch；错误并发会让后保存的旧快照覆盖先保存的修改，因此身份、锁和回读比吞吐量优先。

## 运行时发现，不固化混淆名

先从当前已登录商家页的成功操作、Network 和已加载前端模块确认四类能力：完整商品读取、保存前校验、活动/影响检查、实际保存。历史走通页面曾出现过以下线索，但模块号、导出名和端点都可能变化：

| 历史线索 | 观察到的用途 |
| --- | --- |
| 商品详情导出 `jn({spuId, poiId})` | 读取可再次提交的完整商品对象 |
| 导出 `sI(...)` | 保存前业务校验 |
| 导出 `L0(...)`、`/uniSave/actCheck` | 活动或影响检查；单独调用不会完成保存 |
| 导出 `$W(...)`、`/uniSave` | 实际保存 |
| `/searchListPageNew` | 主列表/搜索；高频调用可能被限流 |
| `/searchByTag` | 按分类读取；只能作为当前页面证实可用后的低频索引回退 |

不要把这些名称当成永久 API。页面模块能复用时，优先调用页面自己的序列化和请求能力；不得复制登录秘密或绕过验证码、人工验证与风控挑战。

## 匹配和 ID 账本

先生成只读匹配账本，每个候选至少记录门店、SPU、稳定 SKU ID、当前店内码/条码、旧 SKU/条码、名称、规格、目标值、来源行和匹配策略。

候选证据按确定性组合，只有结果唯一才进入写入队列：

1. 当前店内码精确等于旧 SKU ID；
2. 当前店内码或当前条码通过账本精确映射到旧条码；
3. 规范化后的旧商品名称与旧规格联合精确匹配；
4. 其他字段只能增强同一唯一候选，不能用模糊名称覆盖冲突。

规范化可统一首尾空白、连续空白、全半角和明确等价的单位书写，但必须保留容量、数量、颜色、尺码等区分规格的语义。名称单独相同、多候选、规格缺失或证据冲突时标为 `ambiguous/unmatched`，不得猜测。

SKU ID、店内码和条码始终按字符串保存与比较，避免长整数被科学计数或截断。列表结果只用于发现 SPU；最终修改和验真按详情中的稳定 SKU ID 定位，不能依赖数组位置。

## 完整 SPU 的安全写入

按 SPU 分组，执行时始终重新读取该 SPU 的最新完整对象，不使用建队时缓存的详情快照：

1. 用稳定 SKU ID 在最新 `skuList` 中找到目标行；找不到或不唯一则失败关闭。
2. 保存 `before`，只修改已授权字段。店内码字段可能在页面模型中同时表现为 `sourceFoodCode`、`skuCode` 或其他名称；只有当前成功请求证明它们应同步时才同时更新。
3. 对完整对象执行页面当前的保存前校验和活动/影响检查；检查接口通过不代表已保存，仍必须调用实际保存能力。
4. 保存后丢弃内存对象，从独立详情读取路径重新取数，并按稳定 SKU ID 比较目标字段。

同一 SPU 是不可拆分的串行关键区。即使多个 SKU 分配给不同来源行，也必须合并进同一次最新快照修改；禁止两个 worker 并发保存同一 SPU。跨 SPU 才能并行。

## 校验、告警和缺失字段策略

开始前冻结本次任务对平台弹窗的处置规则。商品信息问题、活动退出、无条码、必填下拉或其他有业务影响的自动选择，只有用户明确授权后才能自动继续；一次任务的授权不能变成技能的永久默认许可。

- 校验返回结构化缺失字段时，从当前页面提供的有效选项或单位中选择；排除“没有合适/申报”等不能完成校验的占位项。
- 仅当校验明确指向某个 SKU 的非法条码，且平台模型允许无条码时，才对该 SKU 清空条码并设置页面要求的无条码标志；不得清空同 SPU 的其他规格。
- 活动或流量影响检查后仍要执行真正保存。若保存要求带确认标志，必须使用当前页面实际成功请求证明的字段，不猜参数。
- 业务校验、身份冲突和输入错误不自动重试；保留字段级错误和来源行。

## 稳定并发控制

把发现读取、写入和验真分成独立限速器。未经当前门店阶梯验证时，采用以下保守起点，而不是复用历史高并发：

- 列表/分类发现：并发 `1`，请求间加入约 `500–1000 ms` 抖动；成功索引在本任务内缓存，不对每个 SKU 重搜列表。
- SPU 写入：并发 `2`，同 SPU 串行；每次保存后加入约 `300–800 ms` 抖动。
- 独立回读：并发 `2`，可与写池分离，但不能形成无界积压。
- 只有 1 → 2 → 4 的阶梯均保持零限流、零未知写入和 100% 精确回读时，才允许把跨 SPU 写并发提高到 `4`。默认不使用 `8` 路。

这些数值是安全起点，不是平台永久上限。记录滚动延迟、HTTP/平台状态和读回成功率，以门店当前健康动态收缩：

- 首个 `429`：立即暂停新任务领取，遵循 `Retry-After`；没有提示时使用带抖动的指数退避，并把并发至少减半。
- `403`、列表突然显示 0、页面出现“接口请求异常”：视为会话/签名/限流待分类；立刻暂停列表请求和自动刷新。先等待冷却，再用一个只读探针确认恢复；不得并发重试。
- `5xx` 或网络中断发生在写请求后：状态可能已落地，先回读再决定是否重试。
- 连续两个限流窗口或人工挑战：停止批次并持久化续跑点，交给用户处理。

队列领取必须原子化，且任务完成条件是 `done + failed + skipped == total`、没有 worker 仍持有已领取 SPU，而不是“队列索引已领完”。扩容 worker 时共享同一个原子游标和 SPU 锁；最终等待所有原 worker 与新增 worker 都结束，避免提前报完成。

## 物化回读和结果标记

保存响应只记录为 `accepted`。对每个目标 SKU 建立有界物化窗口，使用独立详情读取路径按稳定 SKU ID 检查目标字段；可按短延迟逐步放宽轮询间隔，但总次数和总时长必须有限。

状态定义：

- `success_changed`：写前不等于目标，保存后独立读回精确等于目标；
- `already_target`：写前已等于目标，不发送保存；与“由 AI 修改”分开统计；
- `unknown`：写可能已接受，但物化窗口内无法确定；不得盲目再次保存；
- `failed`：明确业务拒绝、身份错误或最终读回不一致；
- `ambiguous/unmatched`：没有唯一匹配，保持未修改。

每条结果至少保存 `task_id`、来源行、SPU/SKU、匹配策略、`before/target/after`、保存 attempt、警告、worker、`truth_source`、时间和状态。进度在每个 SPU 完成后持久化，使停止续跑不会重复保存已验真的 SKU。

Excel 或结果表中的“AI 修改”标记只能写给 `success_changed`，除非用户明确要求把已是目标值的行也计入；标记前再次核对来源行的名称、规格和目标 SKU，标记后重新打开导出文件并验证数量、身份列、公式和既有样式。

## 商品编辑完成门

只有同时满足以下条件才可称本批完成：

- 所有唯一可执行候选都进入 `success_changed` 或明确的 `already_target`；
- 每个成功 SKU 都有独立详情读回，且按稳定 SKU ID 精确命中目标值；
- 没有 `unknown`，失败、冲突和未匹配项逐条保留，不能被“成功率”吞掉；
- 同 SPU 没有并发保存，所有 worker 均已结束；
- 任务期间的 `403/429`、页面列表异常和退避过程有记录，并发上限不超过当前阶梯证据；
- 外部结果表只标记真正验真的行，导出后已重新打开检查。

建议摘要同时报告：已修改并验真数、已是目标数、失败数、冲突数、未匹配数、SPU 数、峰值并发、限流次数、回读真值来源和结果文件。
