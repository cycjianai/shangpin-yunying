# 美团商品信息编辑、保存、全量快照极速新增与整店清空规范

本模块用于已授权美团闪购/超市门店内的**单品编辑（名称、规格、条码、店内码等）**、**已有店铺快照/货盘商品的全量极速新增复制（8,000+ 商品全量落库）**以及**迁店前清场/错店回滚的整店商品与两级店内分类极速归零**。

---

## 第一部分：单品信息编辑与店内码修改

商品编辑常是“完整 SPU 保存”，不是单 SKU 字段 patch；错误并发会让后保存的旧快照覆盖先保存的修改，因此身份、锁和回读比吞吐量优先。

### 1. 运行时发现，不固化混淆名

先从当前已登录商家页的成功操作、Network 和已加载前端模块确认四类能力：完整商品读取、保存前校验、活动/影响检查、实际保存。历史走通页面曾出现过以下线索，但模块号、导出名和端点都可能变化：

| 历史线索 | 观察到的用途 |
| --- | --- |
| 商品详情导出 `jn({spuId, poiId})` | 读取可再次提交的完整商品对象 |
| 导出 `sI(...)` | 保存前业务校验 |
| 导出 `L0(...)`、`/uniSave/actCheck` | 活动或影响检查；单独调用不会完成保存 |
| 导出 `$W(...)`、`/uniSave` | 实际保存 |
| `/searchListPageNew` | 主列表/搜索；高频调用可能被限流 |
| `/searchByTag` | 按分类读取；只能作为当前页面证实可用后的低频索引回退 |

不要把这些名称当成永久 API。页面模块能复用时，优先调用页面自己的序列化和请求能力；不得复制登录秘密或绕过验证码、人工验证与风控挑战。

### 2. 匹配和 ID 账本

先生成只读匹配账本，每个候选至少记录门店、SPU、稳定 SKU ID、当前店内码/条码、旧 SKU/条码、名称、规格、目标值、来源行和匹配策略。

候选证据按确定性组合，只有结果唯一才进入写入队列：

1. 当前店内码精确等于旧 SKU ID；
2. 当前店内码或当前条码通过账本精确映射到旧条码；
3. 规范化后的旧商品名称与旧规格联合精确匹配；
4. 其他字段只能增强同一唯一候选，不能用模糊名称覆盖冲突。

规范化可统一首尾空白、连续空白、全半角和明确等价的单位书写，但必须保留容量、数量、颜色、尺码等区分规格的语义。名称单独相同、多候选、规格缺失或证据冲突时标为 `ambiguous/unmatched`，不得猜测。

SKU ID、店内码和条码始终按字符串保存与比较，避免长整数被科学计数或截断。列表结果只用于发现 SPU；最终修改和验真按详情中的稳定 SKU ID 定位，不能依赖数组位置。

### 3. 完整 SPU 的安全写入

按 SPU 分组，执行时始终重新读取该 SPU 的最新完整对象，不使用建队时缓存的详情快照：

1. 用稳定 SKU ID 在最新 `skuList` 中找到目标行；找不到或不唯一则失败关闭。
2. 保存 `before`，只修改已授权字段。店内码字段可能在页面模型中同时表现为 `sourceFoodCode`、`skuCode` 或其他名称；只有当前成功请求证明它们应同步时才同时更新。
3. 对完整对象执行页面当前的保存前校验和活动/影响检查；检查接口通过不代表已保存，仍必须调用实际保存能力。
4. 保存后丢弃内存对象，从独立详情读取路径重新取数，并按稳定 SKU ID 比较目标字段。

同一 SPU 是不可拆分的串行关键区。即使多个 SKU 分配给不同来源行，也必须合并进同一次最新快照修改；禁止两个 worker 并发保存同一 SPU。跨 SPU 才能并行。

### 4. 校验、告警和缺失字段策略

开始前冻结本次任务对平台弹窗的处置规则。商品信息问题、活动退出、无条码、必填下拉或其他有业务影响的自动选择，只有用户明确授权后才能自动继续；一次任务的授权不能变成技能的永久默认许可。

- 校验返回结构化缺失字段时，从当前页面提供的有效选项或单位中选择；排除“没有合适/申报”等不能完成校验的占位项。
- 仅当校验明确指向某个 SKU 的非法条码，且平台模型允许无条码时，才对该 SKU 清空条码并设置页面要求的无条码标志；不得清空同 SPU 的其他规格。
- 活动或流量影响检查后仍要执行真正保存。若保存要求带确认标志，必须使用当前页面实际成功请求证明的字段，不猜参数。
- 业务校验、身份冲突和输入错误不自动重试；保留字段级错误和来源行。

### 5. 稳定并发控制

把发现读取、写入和验真分成独立限速器。未经当前门店阶梯验证时，采用以下保守起点，而不是复用历史高并发：

- 列表/分类发现：并发 `1`，请求间加入约 `500–1000 ms` 抖动；成功索引在本任务内缓存，不对每个 SKU 重搜列表。
- SPU 写入：从并发 `1` 开始，同 SPU 串行；每次保存后加入约 `300–800 ms` 抖动。
- 独立回读：从并发 `1` 开始，可与写池分离，但不能形成无界积压；扩容仍受共享 `1→2→4` 资源门约束。
- 只有 1 → 2 → 4 的阶梯均保持零限流、零未知写入和 100% 精确回读时，才允许把跨 SPU 写并发提高到 `4`。默认不使用 `8` 路。

这些数值是安全起点，不是平台永久上限。记录滚动延迟、HTTP/平台状态和读回成功率，以门店当前健康动态收缩：

- 首个 `429`：立即暂停新任务领取，遵循 `Retry-After`；没有提示时使用带抖动的指数退避，并把并发至少减半。
- `403`、列表突然显示 0、页面出现“接口请求异常”：视为会话/签名/限流待分类；立刻暂停列表请求和自动刷新。先等待冷却，再用一个只读探针确认恢复；不得并发重试。
- `5xx` 或网络中断发生在写请求后：状态可能已落地，先回读再决定是否重试。
- 连续两个限流窗口或人工挑战：停止批次并持久化续跑点，交给用户处理。

## 第二部分：全量商品极速新增与快照全店复制引擎（uniSave 协议）

本部分针对将外部店铺/货盘快照（如快送熊全店快照）全量复制并新增落库至目标美团闪购门店的场景。

### 1. 为什么坚决不用美团后台的“批量导入表格（Excel）”？

- **容量受限**：表格单次上限极低（通常 200~500 行），8,000+ 商品需手工切成数十个文件上传，极易产生人工遗漏；
- **信息严重缺失**：表格无法承载美团官方底层复杂的类目专有属性树（`categoryAttrMap`）、绑定属性（`bindAttrMap`）、子规格多角度图、长图详情图列表（`picContent`）、商品资质图与视频；导入后变为残缺裸品；
- **店内两级分类脱节**：表格导入对店内分类匹配脆弱，目标店未提前建好分类时会导致分类错乱或进“未分类”；
- **异步队列排错难**：表格走后台慢速排队，单行数据格式报错会导致整个批次失败且无法准确定位。

### 2. 核心架构：CDP 浏览器会话级原生 RPC 注入

美团闪购商家后台（`shangoue.meituan.com`）部署了 `yodaReady=h5&csecplatform=4&csecversion=4.3.0` 等动态加密签名与反爬策略，外部直接使用 Python `requests`/`curl` 脚本携带 Cookie 发包会被直接拦截并弹出 Yoda 滑块验证码。

**标准解法**：
1. 运营启动带有远程调试端口的常规 Chrome 实例（`--remote-debugging-port=9222`）并登录美团商家后台；
2. 调度脚本通过 **WebSocket** 连接到 Chrome 的 CDP 端点（`Runtime.evaluate`）；
3. 直接在目标页面 iframe（`document.getElementById("hashframe").contentWindow`）上下文中通过原生 `fetch` 发包；
4. **效果**：天然继承浏览器当前的合法会话、Cookie、动态加签与环境指纹，**0 滑块、0 风控、支持 8 并发推流，8,400+ 商品 15~20 分钟全量落库**。

```
┌──────────────────────────────────────┐
│       本地 Python 数据调度中心        │
│  1. 读取快照 -> 组装标准 uniSave 表单   │
│  2. 切分为 Batch 发送给 CDP          │
└──────────────────┬───────────────────┘
                   │ WebSocket (Runtime.evaluate)
                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│           常规 Chrome 浏览器实例 (--remote-debugging-port=9222)         │
│  页面环境：shangoue.meituan.com 内部 iframe (#hashframe)                │
│  hf.fetch("/reuse/sc/product/retail/w/uniSave", ...)                   │
│  ★ 天然拥有完整的 Cookie、Session、CSRF、动态加密与环境指纹，0 风控拦截 ★│
└──────────────────┬─────────────────────────────────────────────────────┘
                   │ 8 并发 Worker 推流 (~7-8 件/秒)
                   ▼
┌──────────────────────────────────────┐
│        美团零售商家后台服务器          │
└──────────────────────────────────────┘
```

### 3. 两阶段核心 API 与字段规范

#### 阶段 1：店内分类树同步与 ID 映射 (`batchSaveHqTags`)
在推送商品前，必须先在目标店铺建齐源店铺的一级与二级店内分类树，并建立映射字典。

- **接口路径**：`POST /reuse/sc/product/hqcc/w/batchSaveHqTags?yodaReady=h5&csecplatform=4&csecversion=4.3.0`
- **请求格式**：`application/x-www-form-urlencoded`
- **核心入参**：`hqccParams=<urlencoded_json>`
  ```json
  {
    "id": 0,                     // 目标店顶级分类ID（新建传 0）
    "name": "速食罐头",          // 一级分类名
    "description": "",
    "sequence": 1,
    "topFlag": 0,
    "isLeaf": false,
    "subTags": [
      {
        "id": 0,                 // 二级子分类ID（新建传 0）
        "name": "网红泡面",       // 二级分类名
        "sequence": 1,
        "isLeaf": true,
        "subTags": []
      }
    ],
    "asyncType": 3
  }
  ```
- **读取目标店映射表**：
  调用 `POST /reuse/sc/product/retail/r/tagList?wmPoiId=...&needSmartSort=true` 获取新店最新全部分类，构造映射字典：
  ```json
  {
    "速食罐头|||网红泡面": { "tagId": 1793522998, "tagName": "网红泡面" },
    "速食罐头|||自热速食": { "tagId": 1793522999, "tagName": "自热速食" }
  }
  ```

#### 阶段 2：单品与多规格创建核心接口 (`uniSave`)
- **接口路径**：`POST /reuse/sc/product/retail/w/uniSave?yodaReady=h5&csecplatform=4&csecversion=4.3.0`
- **Content-Type**：`application/x-www-form-urlencoded`
- **核心表单参数表**：

| 表单 Key | 必填 | 类型 | 规范与说明 |
| :--- | :---: | :--- | :--- |
| `name` | 是 | String | 商品标题（需清洗掉前缀无用噪点） |
| `categoryId` | 是 | String/Long | **美团官方标准三级类目 ID**（如 `100123`），必须是美团标准类目，切勿混淆为店内分类！ |
| `wmPoiId` | 是 | String | 目标门店唯一标识 |
| `tagList` | 是 | JSON String | 关联的店内分类数组，如 `[{"tagId":1793522998,"tagName":"网红泡面"}]` |
| `skus` | 是 | JSON String | SKU 数组字符串（包含规格、条形码、价格、库存、重量等） |
| `picture` | 是 | String | 商品主图，多张 URL 用逗号 `,` 分隔 |
| `picContent` | 否 | String | 商品详情长图，多张 URL 用逗号 `,` 分隔 |
| `sellStatus` | 是 | Integer | `0` 为下架/无货；`1` 为上架销售 |
| `categoryAttrMap` | 否 | JSON String | 美团类目属性映射（品牌、产地、保质期等） |
| `bindAttrMap` | 否 | JSON String | 绑定属性映射，默认 `{}` |
| `spuSaleAttrMap` | 否 | JSON String | 销售属性映射，默认 `{}` |

- **`skus` 数组内部核心结构（避坑重点）**：
  ```json
  [
    {
      "spec": "默认规格",                // 多规格传具体口味/型号（如"39码"、"原味"）
      "price": 9.9,                     // 售卖价（元）
      "upcCode": "6901234567890",       // 13位国标条码
      "weight": 500,                    // 净重
      "weightUnit": "g",                // 重量单位：g / kg / ml
      "stock": 0,                       // 建议新录入商品初始库存设为 0
      "minOrderCount": 1,               // 最小起购数，默认 1
      "commonProperty": {               // ★ 致命避坑点：无条形码商品必须配置！
        "allowUpcEmpty": "true"          // 若无此参数，美团接口会直接阻断并报错“商品条码不能为空”
      },
      "skuCategoryAttrMap": {}          // 子规格专有属性（如有）
    }
  ]
  ```

### 4. 关键避坑准则

1. **新建商品主键必须清零**：
   快照中的 `spuId`、`skuId`、`id` 是老店铺的主键。复制到目标新店时，**必须将 `spuId`、`skuId`、`id` 全部重置为 `0` 或空**，美团后台才会将其识别为新建商品并分配新 ID。
2. **无条形码商品防护**：
   对于生鲜、散装、小五金等无国标条码的商品，SKU 中必须携带 `"commonProperty": {"allowUpcEmpty": "true"}`。
3. **主图 URL 清洗**：
   快照中的图片 URL 往往带有图片处理参数（如 `@500w_500h...`），导入时使用 `u.split('@')[0].split('#')[0]` 还原为高清无损原图。
4. **两阶段执行切勿并发混杂**：
   必须确保店内分类树全部创建完成并建立好映射后，再启动商品批次导入；严禁边插入商品边建分类，以免引发美团分类树并发死锁。

### 5. 三级容错自愈与频控重试引擎

快照中的部分历史商品，其部分类目属性可能被美团新规范弃用。如果直接报错会导致批量中断。  
**必须在注入代码中实现三级降级与频控指数退避**：

1. **第一层（Rich 完整模式）**：全量携带属性、详情图、视频、资质图发起保存；
2. **第二层（Strip Attrs 属性降级）**：若美团返回类目属性校验错误（如 `categoryAttrMap` 某字段不合法），立即将 `categoryAttrMap="{}"`、`bindAttrMap="{}"` 剥离重试，95% 的属性冲突可通过此步自愈；
3. **第三层（Strip Media 媒体降级）**：若视频或导购图格式校验失败，清空 `video="{}"`、`cpvGuidePicList="[]"` 再次重试，确保商品能成功录入；
4. **并发锁与频控退避**：若美团接口返回 `/并发写入|系统异常|频繁|稍后/`，执行 `sleep 1000 * (attempt + 1)` 退避重试（最多 3 次）。

## 第三部分：整店商品与两级店内分类极速清空协议（迁店清场 / 错店回滚）

当用户明确授权清空目标美团闪购门店的全部商品与全部店内分类时，严禁逐页人工勾选删除或乱序硬删一级分类，严格遵循以下两阶段纯内存协议（实测 8,400+ 商品与 600+ 两级分类可在数分钟内 100% 归零）：

### 1. 运行时锁定与防丢 Chunk 红线

- **必须驻留在商品列表页**：确认 `#hashframe` 当前 URL 为 `/reuse/sc/product/page/list/product/list`（此时 `win.webpackChunkpackage_list` 正常挂载）；
- **回收站页面陷阱**：切勿在回收站页面（`/reuse/sc/product/views/product/recycle`）执行注入——回收站属于独立前端子包，不存在 `webpackChunkpackage_list`，直接读取会报 `Cannot read properties of undefined`；
- 每次注入通过随机 Chunk ID 提取模块加载器：`win.webpackChunkpackage_list.push([[Math.random()], {}, (r) => { req = r; }])`。

### 2. 阶段 1：全店商品批量移入回收站（`req("49308")`）

- **全量分页拉取**：调用 `await req("49308").gX({ wmPoiId, needCount: 1, needCombinationSpu: 2, needTag: 0, pageNum: 1, pageSize: 50 })`（或同模块封装的 `/reuse/sc/product/retail/r/searchListPageNew`），必须携带 `needCombinationSpu: 2` 确保组合商品一并检出；
- **为什么不能只靠“删除分类连带删商品”**：`req("24567")._R` 虽支持 `type: 1`（`TAG_AND_PRODUCT`），但它只能删除挂载在特定分类下的商品，对“未分类”商品或跨分类残余无效；整店清空必须先按商品列表循环调用 `req("49308").kw`（`batchDeleteWithSpu`，传入当前批次逗号分隔的 SPU ID 与 SKU ID 列表）直至 `queryCount.all === 0`（在售、售罄、下架、草稿箱全部归零）。

### 3. 阶段 2：两级店内分类树“自底向上”逆序归零（`req("24567")`）

- **读取完整分类树**：调用 `const res = await req("24567").nv({ poiId: String(wmPoiId), needSmartSort: true })`，优先取 `res.originTagList || res.tagList || []`；
- **自底向上逆序铁律（严禁先删父分类）**：美团店内分类存在父子外键约束，若一级主分类下仍含二级子分类，直接删除一级分类会被后端拒绝。必须拆分为两轮依次清理（推荐 `4` 路并发 + 批间 `80ms` 间隔）：
  1. **第一轮（先清空全部二级子分类 `level 1`）**：遍历每个一级分类 `t.children`，收集所有二级子分类 `c.id`，调用 `await req("24567")._R({ wmPoiId: String(wmPoiId), tagId: c.id, type: 2 })`；
  2. **第二轮（再清空全部一级主分类 `level 0`）**：待二级子分类 100% 删除完毕后，遍历所有一级主分类 `t.id`，调用 `await req("24567")._R({ wmPoiId: String(wmPoiId), tagId: t.id, type: 2 })`；
