# 牵牛花批量操作选择与请求粒度

只在大量同类字段操作、逐商品页面切换成为瓶颈，或总部零售价补齐时加载。此文件提供路径选择，不新增其他字段的 writer。

## 先检查业务入口，再决定是否逐 SPU 编辑

| 当前事实 | 使用的路径 | 保留的验证 |
|---|---|---|
| 官方有目标字段专用导入，按稳定 SKU 定位，能限制副作用 | 官方模板 + 单次批次提交 | 租户、SKU 清单、文件摘要、限定影响范围、独立回读 |
| 列表已完整包含所需 SKU 字段 | 冻结筛选后分页读取，页内投影必要字段 | 总数、页码、SPU/SKU 去重、身份和字段形状 |
| 用户授权的源货盘有完整版本/导出/API | 一次只读提取并建立本地索引 | 来源权限、版本、完整性、逐规格来源证据 |
| 字段只能通过完整对象保存或官方导入会扩大影响 | 原有精确编辑页 writer | 最新完整对象、字段白名单、单 SPU 单写者、详情回读 |
| 属性/图片/审核规则不被价格导入覆盖 | 继续原属性/图片/不可售任务合同 | 不把调价能力推广成任意商品修改能力 |

优化的是请求次数和对象物化次数。先同页顺序分页、一次本地匹配、少量官方导入；只有端到端实测更快才增加并发。
不要为每个商品建页面，也不要为一万次名称搜索重复登录高效版。不存在合适批量能力时保留原有路径。

## 当前列表原生证据与只读分页

1. 先打开用户授权的列表并设置实际筛选，监听当前文档的原生成功请求，再执行查询或真实翻页。
   相同筛选的“查询”可能被页面缓存；没有新请求时用已观察到的分页控件，不能拿历史回执冒充当前证据。
2. 列表通常是 `POST /qnh-gw3/api/product/tenant/page-query`。冻结真实 body 中的标签、类目、状态等所有筛选，
   原生 `page/pageSize` 和响应 `data.total`；标签必须按当前平台返回的类型 ID/标签 ID 唯一确定。
3. 从成功请求 URL 读取 `csecversion`，不能按租户猜测。历史支持 `4.2.0/4.2.4/4.3.0`；未知版本停止自定义请求。
   每个查询对最终 URL + POST + JSON body 调用当前页面 `H5guard.sign`，校验本次返回 A9 与版本；
   允许的 opaque A9 只继承本次精确签名绑定，不用于发现版本。保留同版本 403 有界恢复合同，禁止版本轮盘。
4. `Content-Type`、`M-APPKEY`、`qnhReferrer` 等只从当前原生请求取白名单必要值；Cookie 由当前浏览器自动携带。
   不读/导出 Cookie 或 storage，不把 `mtgsig`、完整请求头写入文件。公开文档中的端点不是固定请求包。
5. 此次同页 `pageSize=100` 成功；其他会话先验证服务端实际返回的 `pageSize` 和完整列表，再使用该页大小。
   不假设增大到 500/1000 一定更快或不会被截断。只有全部分页、总数、唯一 SPU/SKU 和租户一致时置 `complete=true`。
6. 页内只返回对账需要的数据：SPU、名称、SKU、规格、条码、总部价、原有价格和约定保护字段。
   每页落 checkpoint，不在工具输出打印全部商品/DOM，不反复把全部原始详情物化到 Node。
7. 页面、文档、身份或筛选变化后停止新查询并重新取得原生证据。同数量不同 ID、翻页重复、漏 SKU 或字段缺失都不能算完整。

只有原生列表确实包含目标字段时，最终列表物化读回才可替代逐商品详情；列表未包含的保护字段需要补充适当的正式读取，
不得把未观察字段报告为“全部未变”。分页不是数据库事务；批次前还要回查目标旧值，最终范围变动要报告并处理。

## 源货盘一次读取与本地索引

允许用户提供的完整导出、当前已授权 API，或明确在本项目授权范围内、与高效版 UI 相同的只读数据源。
数据库不是跳过登录或授权的通用后门；无法证明来源访问范围时复用合法登录或请用户登录。不要索取账号密码。

冻结来源系统、货盘版本、完整计数、币种和价格字段。若有多个货盘，先用任务上下文、条码/名称/规格交集缩小范围；
仍有多个合法来源且价格不同才询问。不能使用“查到的第一个货盘”、最低价、活动价或相近名称代替来源确认。

读取后按条码与 `(规范化商品名称, 规范化规格)` 建索引。金额用 Decimal，ID/条码从读取到 Excel 全程保留文本。
本次复制商品的一部分条码就是目标 SKU ID，因此仅条码匹配会漏掉这些商品；这种已确认的生成条码可用唯一名称+规格补足。
不删除名称末尾数字、计量单位、包装数、容量或规格值；候选价格相同也不能把身份冲突当成唯一匹配。

## 性能与授权边界

- **架构标准**：对于必须通过接口逐商品修改完整对象的治理任务（如渠道类目补齐、全量属性治理、状态同步等），**统一强制采用【4 Tabs + 12 并发 Workers】分布式架构**：
  * **4 Tabs**：复用 Chrome 内 4 个独立页面的 `window.H5guard.sign` 作为分布式签名收银台，解决浏览器单线程 JS 锁竞争；
  * **12 Concurrency**：12 个异步 Worker 分布式拉取与组装数据，按 3:1 比例派发签名，完全跑满服务端网关 Socket 连接池且不排队；
  * **实测吞吐**：单商品全流程 ~2.3 秒，大盘跑速稳定达到 **250~300 SPU/分钟**，100% 成功率且 0 平台风控降级。
- 浏览器和批处理沿当前项目受控运行入口，页面由执行器受控管理并在任务完成时释放；
- 记录读取、匹配、上传、提交、等待物化、回读和复扫的墙钟及请求数。源索引命中不等于平台写入成功。
