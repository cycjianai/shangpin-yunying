# 牵牛花受保护请求工程维护合同 v1

本合同只适用于牵牛花受保护请求入口的诊断、设计、修复与灰度：HTTP 403、H5guard/A9、页面或 Cookie 身份、成本同步、保质期、受管 Chrome、持久租约、健康检查和协议版本兼容。实际商品读取、填充、图片治理、不可售清退、保存后回查和运营表导出继续走商品治理执行轨道。请求入口成功不等于业务成功。

## 1. 当前仓库是真源

动工前依次完整阅读当前项目的 `AGENTS.md`、`docs/pitfalls.md`、`docs/agent-rules/qnh-protected-request.md`、`docs/services.md` 和相关 OpenSpec；文件存在性与实际模块位置用 `rg --files` 确认。正式生产源码唯一根为 `/home/saas/repo`，不得假定旧项目目录、历史 release 或候选目录仍是运行真源。

项目内的受保护请求规范优先于本通用合同。只有经过真实证据验证、可跨任务复用且不泄露敏感信息的结论，才回灌本 Skill；不得用旧 Skill、GitHub 旧包或历史成功样例整文件覆盖当前生产实现。

## 2. 传输画像必须隔离

- `current_tab_extension`：只使用用户当前绑定 document/tab 的页面上下文和 Main World 直接签名证据；禁止读取、导出、注入或跨任务缓存 Cookie，也禁止把外部签名、历史 A9 或其他标签页证据当成本页证据。
- `backend_managed_context`：只有当前项目已经存在并明确授权的后端受管方案才可使用。Cookie 必须按精确 QNH 域名、账号、tenant/store、用途和租约隔离，不得写入命令行、环境变量、健康接口或普通日志；Chrome/CDP 仅绑定 loopback，页面所有权和跨进程互斥必须落在 PostgreSQL 等持久状态中，本地锁只能作为第二道门。
- 美团及其他平台必须使用自己的独立 adapter、登录态、签名版本、请求包和回查事实。不得把牵牛花 Cookie、A9、circuit、页面租约或 writer 传播到美团，也不得反向复用美团签名细节。

画像、身份或页面所有权不明确时零发送。两个 QNH 传输画像可以在同一系统中并存，但不得共享 Cookie、页面证据、签名缓存或弱成功判断。

## 3. 失败先分类，禁止猜测式重试

诊断必须先回答“是否发送、发送到哪里、使用什么 profile、返回什么”，并保留下列稳定低敏原因：

- 请求前页面证据不足：`qnh_page_context_unavailable`；
- tenant/store/SPU 不匹配：`qnh_store_context_mismatch`；
- 无法生成 request-bound 签名：`qnh_signature_unavailable`；
- URL、A9 与 profile 版本不一致：`qnh_signature_version_mismatch`；
- 登录明确失效：`qnh_login_expired`；
- 持久页面租约被占用：`qnh_context_busy`；
- 首次 403 同 profile 恢复后仍拒绝：`qnh_risk_rejected`；
- HTTP 成功但平台业务失败：`qnh_platform_error`。

日志至少区分 `sent=false` 的本地失败、真实 HTTP 状态、平台业务 code 和结果未知；不得把 Cookie 缺失、签名失败、403、业务失败或查询超时压成同一个错误，也不得把状态未知解释成平台未受理。

## 4. 协议与签名兼容

牵牛花必须保留 `4.2.0`、`4.2.4` 和项目规范已验证范围内的 `4.3.0`。版本只能由当前真实 route、功能入口、document 原生成功证据和对精确 URL/方法/body 的 H5guard/A9 绑定共同选择；列表 query-only 证据不得外推到编辑、上传、预检或保存。明确版本的 A9 必须与 URL/profile 一致，opaque A9 只能在本次精确请求直接签名或逐字回显绑定成立时继承已知版本，不能用于发现新版本。

禁止 `4.2.0/4.2.4/4.3.0` 版本轮盘、403 后切版本、按账号白名单选版本或静默降级。首次真实 403 只允许刷新原绑定且无未保存风险的页面一次，重新确认同一身份并按冻结的同一 profile 重签；第二次失败立即返回 `qnh_risk_rejected`、打开精确 circuit 并停止。

引入“更好的技术方案”必须提交兼容证据矩阵：旧插件响应、新插件响应、每个已支持 profile、页面/profile 不匹配、首次刷新同 profile 重试、第二次停止、query-only/写操作边界和零敏感信息泄露。只有新旧合同并集通过，才允许增量接入；不得以删除旧 profile、放宽身份校验或要求全部客户升级换取表面速度。

## 5. 执行架构与资源门

API 层只负责输入校验、入队、状态查询和低敏诊断；浏览器获取、页面导航、精确签名、fetch、分页和同 profile 恢复必须由拥有页面上下文的插件或 Worker 执行。任务、账号、tenant/store、tab、profile、SPU、call type 和 fence 必须进入持久租约或幂等键；进程重启不得丢失写意图、未知结果屏障或 provider 受理凭证。

浏览器优先复用已验证热页或既有受管 Chrome，禁止每个分页启动 Chrome、每商品新开标签、用空白页代替真实页面，或把 CDP 暴露到公网。所有工程 canary 也必须先通过统一资源准入：默认一个热页，只有端到端更快且资源余量持续通过时按 `1→2→4` 升档，4 是硬上限；压力出现后单调降档，任务结束必须回收自有页面。

## 6. 成本同步与保质期的灰度顺序

先用当前登录账号做只读首页，再做完整分页和本地核对；只读阶段成本写入、商品写入、provider submit 和计费增量必须全部为零。确认页码、总数、去重、身份和失败分类正确后，才可按既有 OpenSpec 打开最小写 canary。成本同步不得顺手改成本公式、商品匹配或财务口径；保质期是独立动作，必须单独验证其请求包、写入结果和物化回读。

真实发布若涉及写入，按 `1→5→20` 的账号/门店 canary 扩大，每档都核对成功率、403、身份错配、资源峰值、重复提交、未知结果和回读一致性。任一门失败立即关闭新增 route/action，保留旧健康链路；回滚依赖 feature flag、路由门或明确配置，不得把静默旧链当长期解法。

## 7. 可观测性、安全与完成口径

低敏结构化日志记录 `trace_id`、任务与业务源键、transport/profile、`sent`、HTTP/业务状态、原因码、签名尝试次数、租约/fence、分页进度和阶段耗时。禁止记录 Cookie、Token、完整 A9、密钥、完整请求体、图片 base64 或用户敏感原文。健康接口只返回 ready/busy、低敏身份哈希、页面 host/route、协议画像、最近错误码和时间，不得成为凭证导出接口。

工程交付顺序固定为：证据优先只读诊断 → 当前 OpenSpec/影响面确认 → 失败矩阵与 5–10 个 mock 合同样例 → 隔离实现 → 专题与历史回归 → 当前登录态只读 canary → 获批写 canary → 分档发布。Mock、单测和构建通过只能宣称离线完成；没有真实登录态证据时必须明确“实机兼容尚未验收”。

受保护请求轨道最终只证明请求入口可用、身份正确、版本兼容且资源受控。后续业务动作仍必须由平台 adapter 独立完成，再按统一业务成功合同核验物化回读、结构正确、非目标保护、任务终态和统一七表；任何请求 2xx、签名成功或保存受理都不能替代这些完成门。
