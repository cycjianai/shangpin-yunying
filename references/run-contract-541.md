## 1. 使用边界

本合同用于新的牵牛花账号或新的不可售筛选集合。复用的是处理规则、正式提示词来源、脚本、字段合同和
反馈闭环。允许复用本 Skill 已启动且确认空闲的浏览器登录窗口，但不得在 profile/CDP 间复制 Cookie，
也不得复用旧任务的 tenant/store、SPU、provider 任务号、上传回执、checkpoint 或 write intent。

只有任务路由为 `unavailable_one_pass` 时读取和执行本合同。`channel_attributes_only`、
`qualification_images_only` 和 `plugin_attribute_fill` 不得把本合同的一次过采集、OCR、博查或图片阶段叠加到自身流程。

用户登录后，默认只控制当前隔离 Chrome/CDP；不要求登录原点账号，也不依赖浏览器插件执行。
允许调用项目现有的博查信息解析和正式专项图 provider，但必须沿用其密钥读取、幂等、轮询和低敏日志合同。

## 2. 新账号启动

1. 先只读发现既有 Skill 会话；确认没有运行中/待续传任务且端口、进程和身份健康时复用原 profile、display、CDP、VNC/noVNC。用户明确要求新开，或旧会话忙碌、未知、不健康时才新建；无论哪种情况都为本任务新建 run-dir，全部端口仅监听 loopback。
2. 把对应 SSH 隧道命令交给用户；用户完成登录或切换账号后运行 `preflight`，把用户指定 CDP、实际 profile、tenant/store、
   店铺名、页面 route、筛选 URL 和 run-dir 落盘为 `session_identity.json`。任一不符时，本会话读数全部无效，
   读取以外的网络动作零发送。复用窗口不构成租户身份授权，只有本任务的新 `session_identity.json` 才是授权证据。
3. 关闭全部商品编辑标签，只保留首页和商品主档；后续每个 SPU 完成或失败后都立即关闭编辑标签。
4. 冻结当前筛选的全部分页，记录总数、唯一 SPU 数和集合哈希；读取全部详情、审核原文和官方建议。
   用户给出原始表时保存只读副本和 SHA256，并始终区分平台全集、原始交集和运行期新增。
5. 生成错误矩阵和起始审计表。所有写入必须属于冻结 manifest，不按页面当前活动行猜商品。

## 3. 报错路由

### A. 平台或商品自身已有确定事实：`safe_direct`

- 平台明确建议：字段对齐、候选存在且无包装/口味/规格冲突时采用。
- 类目和品牌：只用当前账号实时官方推荐或品牌库真实 ID；HTTP 200 后回读为空视为失败。
- 标题、SKU、功率、数量、包装方式：只取标题、SKU、同 SPU 包装/铭牌中的逐字事实。
- 主图最低数量：同 SPU 详情图优先；图库完整标题候选必须目视核对品牌、型号、规格和图案。
- 详情图为空：只复用当前 SPU 主图。

### B. 普通信息缺失：`bocha_resolve`

复用项目 `/home/saas/repo/backend/app/services/toolbox/product_fill_resolution/`：

- `discover_qnh_public_web_contexts` 发现当前缺失字段。
- `build_resolution_request` 冻结字段键、候选和商品身份。
- `resolve_bocha_search_provider` 读取已配置的博查 provider，不输出密钥。
- `BochaSearchClient` 每个稳定业务键最多搜索一次。
- `DeepSeekKeyedFieldClient` 每个稳定业务键最多解析一次。
- `_validated_resolution` 通过后才生成牵牛花字段计划。

Checkpoint 必须在每次外部调用后立即落盘。`terminal`、`provider_unresolved`、合同拒绝和无结果均不得通过
改标题、换 query 或换 run-dir 自动重查。博查只补普通信息；CCC、备案、许可证、厂址、条码等监管事实
仍需精确官方或同款实物证据。

### C. 图片要求：`reference_generate_or_reuse`

适用于配料/营养成分图、背签图、包装标签图、尺寸图和纺织吊牌/洗唛：

1. 先扫描同 SPU 主图、详情图、专项图和目视通过的精确同款图库候选。
2. 有真实同款图片时优先直接复用；需要清晰化/排版时调用项目正式提示词来源
   `product_fill_special_picture_prompt` 与既有 `qnh_main_image_art` provider 合同。
3. 每个 `tenant + SPU + picture_type + prompt_hash + reference_hash` 只允许一个稳定业务任务。
4. Submit 前落盘 claim；拿到 `provider_task_id` 后只 query 原任务，不因超时、失败或审核未退出而重提。
5. 生成图必须目视/OCR 对照品牌、型号、规格、包装件数、尺寸、配料文字、营养数值和条码。
6. 通过后上传牵牛花图床，保存完整 URL 集合，并逐图片槽位回读。

生图前先做槽位审计。默认映射为 3 包装标签/参数、4 3C/品质、5 配料营养、6 纺织使用说明、
7 吊牌/洗唛、8 背签、13 尺寸；仍需实时核对 title/description/numLimit。已有制品落错槽时复用 URL 迁移，
不得重新生图或上传。同槽多图先合并最终 URL 集合，只保留一次保存目标。

食品配料/营养图使用项目正式提示词，不自行改写核心变量：

```text
商品名称：{商品名称}
商品主图：{商品主图}
当前类目需上传清晰完整的商品配料、营养成分表和条码图片，建议上传电子扫描图或平面设计图；若实拍图片，建议对关键信息特写拍摄，保证文字清晰、背景整洁。
```

背签使用项目唯一 canonical 五项提示词。包装标签必须有真实厂名、厂址和型号；尺寸图必须至少有可追溯的
尺寸事实；纺织图必须能逐字核验材质、安全类别和洗涤说明。

### D. 法定材料：`regulated_evidence_only`

3C、化妆品/医疗备案、农药/生产许可证、检验报告、公章和注册证只允许：

- 博查、CQC、国家药监或其他权威登记中品牌、精确型号、制造商完全一致的现有记录；或
- 当前 SPU 真实包装、铭牌、证书和背签。

查不到时记录阻塞。不得生成证书、编造编号、使用固定值或借用近似型号材料。

### E. 禁售或经营范围：`manual_block`

平台明确禁售、超经营范围或账号缺少经营资质时停止自动修改，不通过删词、换图或猜类目规避。

## 4. 一次过计划器

1. 先完成全量详情、官方建议、博查普通字段、同 SPU 图片和条码证据采集。
2. 每个 SPU 合并标题、SKU、类目、品牌、普通属性、主图、详情图和专项图为一份 `one-pass` 计划。
3. 每个字段记录 `expected_old`、`new_value`、证据类型、证据 URL/图片和处理路由。
4. 跨食品、日百、家电、服饰抽取 5–10 条 PoC；全部 dry-run 通过后实际保存并回读。
5. PoC 必须 100% 满足：业务成功、目标字段一致、非目标字段未清空、全部门店覆盖、编辑标签已关闭。
6. PoC 通过后默认单热页；只有同量 canary 更快且资源余量持续通过才按不同 SPU `1→2→4` 扩量；同一 SPU 始终串行执行读详情→合并→保存→回读。

## 5. 保存与审核反馈闭环

每个 SPU 都按以下状态机执行：

```text
planned → dry_run_passed → save_accepted → readback_verified
                                      ↘ readback_failed
readback_verified → materialized_waiting_review
materialized_waiting_review → exited_unavailable
                            → same_reason_still_present
                            → new_reason_after_review
```

- 图片物化需要三面证据：实际保存请求受理、独立详情精确回读、刷新/重开编辑页后正确槽位仍可见。
  普通字段可按既有兼容合同省略页面面；出现详情/UI 不一致、标品库限制或保存零请求时页面面强制。
- `readback_verified` 只证明写入物化，不等于审核通过。
- 立即、约 5 分钟、约 10 分钟以及用户后续要求时重新冻结；只有连续两份数量和 SPU 哈希一致才叫稳定快照。
- 同一原因仍在时，先确认目标字段/URL 是否还在、槽位是否正确、是否覆盖全部门店、审核是否仍指向旧快照。
- 字段/URL 已精确存在时不重复保存；provider 已接单时不重复生图。只有出现新证据、字段路径错误、制品事实错误
  或新的审核原因，才建立增量修订计划。
- 把“原原因消失但出现新原因”记为 `new_reason_after_review`，不能把它归为本轮失败，也不能反复写已解决字段。

## 6. 幂等与性能

- QNH 写意图至少按 `tenant + store + SPU + field/picture_type + expected_old + new_hash` 持久化，跨 run-dir 查重。
- Provider claim 至少按 `tenant + SPU + picture_type + prompt_hash + reference_hash` 持久化，跨 output-dir 查重。
- HTTP 结果未知但可能已受理时只回读，不重复 final save。
- 字段保存并发可从 10 个不同 SPU 起步；遇到 429、403、登录失效或回读不一致立即降窗/暂停。
- OCR/Tesseract 每账号最多 4 workers，同机多账号推荐串行；长扫描按 10 SPU 小分片落盘。
- 外部图片 provider 默认小并发，任何业务键都只 submit 一次。
- 单商品保存吞吐按整批墙钟/商品数统计，平台审核等待不计入 10 秒目标。

## 7. 审计与完成口径

字段级审计至少包含：账号/tenant、SPU、商品名、写前审核原文、路由、字段/图片类型、旧值、新值、证据、
博查查询次数、provider 调用类型、保存业务结果、回读结果、审核复扫结果、最终剩余原因和时间。

最终报告分开统计：

1. 起始不可售和唯一 SPU。
2. 计划、提交、回读通过、失败、阻塞。
3. 修改字段数和新增图片槽位数。
4. 已退出原集合、仍不可售、审核中新回流。
5. 外部 submit/query 数、重复 submit 数（必须为 0）。
6. 平均单商品耗时、P95、OCR/图片处理耗时。
7. 平台当前全集、原始目标仍不可售/已退出、运行期新增；批次效果按目标 cohort 统计，不只看平台总量。

禁止把 HTTP 200、业务码 0、图片 ready、上传成功或字段回读成功单独表述为“已全部可售”。

## 8. 已验证经验

- 品牌自由文本可能 HTTP 200 但回读为空；必须查询当前渠道品牌库并写真实 ID。
- 平台推荐可能字段错位或与标题包装冲突；“官方推荐”仍需冲突门。
- 图库完整标题搜索会命中错品牌、错型号、错规格；必须目视核验，查询第一张不能自动采用。
- 重复售后/提示图不能用于凑主图最低数量。
- OCR 10 workers 会导致 CPU 饱和/超时；4 workers 和 10 SPU 分片更稳定。
- 生成图即使清晰、上游 ready、平台暂时出队，也可能新增错误厂家、型号、尺寸、条码或许可证；必须逐事实验收。
- 主图优化可能让商品先退出，但随后因配料、背签、3C等独立原因回流；反馈闭环必须按原因变化处理。
- 同一专项图在详情顶层回读存在，不一定代表编辑页可见或标品库允许保存；需要页面和真实请求双证据。
- 审核通常数分钟，慢时 1–2 小时；等待不是重复保存或重复付费的理由。
- 背签与包装标签不是同一槽位；把背签写入 3 号槽会造成顶层似有图、实际 8 号背签仍为空。
- 详情顶层有 URL、页面临时预览或点击保存都可能是假成功；标品库商品可能零请求并在刷新后丢失。
- 连错 CDP/tenant 后得到的数量与集合全部无效；账号隔离门必须前置到读取、上传和保存。

## 9. 可复制启动命令

在已安装本 Skill 的电脑上，用户只需发送：

```text
使用 $qnh-fill-channel-unavailable。
为这个牵牛花账号建立全新隔离 Chrome/CDP/noVNC 会话，把 SSH 隧道命令发给我，等我登录。
登录后只处理我当前筛选的“渠道不可售”全部商品，不复用其他账号的 profile、Cookie、端口、任务号或收据。
完整执行 541 条实战复用合同：冻结全量清单，逐 SPU 读取审核原文；普通信息优先平台/同 SPU 事实，缺失信息走项目博查字段合同；配料营养、背签、包装标签、尺寸和纺织图片走项目正式提示词与一次 submit 合同；法定证照只用真实材料。
先做跨类目 5–10 条 PoC，100% 保存并回读后按不同 SPU `1→2→4` 扩量，全程断点续跑；每个商品完成后关闭或复用编辑标签。
保存后做审核反馈闭环，不重复写已物化字段、不重复付费；导出字段级 XLSX/CSV，并分别汇报写回成功、审核退出和仍不可售数量。
```
