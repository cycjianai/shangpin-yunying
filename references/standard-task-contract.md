# 既有 QNH 执行器合同

本文件用于 `qnh_task_contract.py` 管理的五种模式。平台/任务总入口是 `route_skill.py`；
总部零售价导入、映射复核、门店替换和其他平台使用各自任务合同，不进入本执行器。

## 会话与续跑

优先复用当前已授权的登录态，核对平台、tenant/store、目标集合及实际执行占用。发现忙碌页时不抢占；
其他任务的历史 checkpoint 或持久租约标签本身不证明当前页正在执行，应核对当前执行权与进程事实。
登录失效时让用户在原安全窗口重新登录，不因此自动新建 profile。

独立新任务创建自己的 run-dir；恢复原任务保留原 manifest、checkpoint、写意图和受理回执。
切换可用浏览器时重新验证身份与执行权，不能丢掉原任务防重记录，也不能仅因 tab/profile 改变就重新提交。
本执行器冻结文件哈希；文件更新后须按兼容性核对恢复，不能篡改旧哈希或新建空任务绕过未知写屏障。

用户明确要求扩展执行时使用当前标签页扩展 transport，并生成 canonical receipt；不要把直连结果冒充插件结果。
登录窗口打开与连接方式见 [运行手册](operations.md)。

## 渠道属性完成条件

1. 冻结源清单并去重；正式 reader 明确不存在的商品单列 `missing_on_platform`。
2. 只治理任务指定的渠道属性。当前推荐、同 SPU 等价事实及标题/SKU 事实要与字段候选和结构一致。
   模板存在、值非空和结构校验通过不能证明商品事实正确；不以默认矩阵猜保质期、产地、许可证等事实。
3. 保存前校验 expected-old；同 SPU 合并写入。保存失败、超时或结果未知先独立回读，只有确认的残余才进入补写计划。
4. 完成后重新读取全部平台现存目标并运行 `validate_channel_contracts.py`；`products_with_issues=0`、
   `issue_count=0` 仅证明结构通过，还须目标值证据、非目标保护及每个商品的唯一终态齐全。
5. 保存交付率、结构通过率、真实材料覆盖率和审核退出率分别统计。

既有 `channel_attributes_only` 动作合同的 OCR、Web、模型和图片预算为零；需要这些能力时先核对任务范围，
不得在这个执行器里暗中扩展动作。其他模式按自己的合同使用相关能力。

## 性能与恢复

同一 run 中完整且集合哈希一致的只读索引、建议和计划可以复用；写前仍查目标旧值。
完成窗口不重复打开页面或保存。预演 `previewed` 与正式写入终态分开，预演失败可补检失败项。
资源和并发以 [资源合同](runtime-resource-contract-v1.md) 及执行器实际边界为准，批次总数不能当作并发数。

只在实测证明同一字段形状与取值证据仍有效时减少重复读取或预演。历史耗时和成功批数不是跳过事实检查的通行证。
发现可复用新根因才更新 Skill；不把单次网络波动或某个商品的参数写成通用规则。

## 标准运营工作簿

用户需要标准运营报告时，按 [统一输出合同](core/output-contract.md) 导出七表。
既有 QNH 执行器使用 `standard_output_name.py`、注册 exporter、validator、completion gate 和 handoff gate；
其他任务使用自己的兼容入口。`validation_only` 表格不能冒充实际写入成果。

历史执行记录只能从同租户、同商品、逐字段可核验的保存与独立回读证据补入；计划、预演或保存受理不算已执行。
