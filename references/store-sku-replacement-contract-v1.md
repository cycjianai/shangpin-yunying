# 牵牛花门店旧新 SKU 替换迁移合同 v1

## 1. 冻结范围

- manifest 只能来自用户指定的新 SKU 列非空行；其他行处理数必须为 0。
- 每行固定映射 `source_sku -> target_sku`，两者按文本处理；任一 SKU 空、相同、重复映射或多对多冲突时失败关闭。
- 相同 SKU 行不得因为已经迁移过资料而例外进入删除集合；它只有一个门店实体，删除“源”会同时删除“目标”。发现该冲突就停止该行删除；只有已有证据证明发生误删时才按恢复授权执行补偿，不能仅凭映射冲突重新覆盖商品。恢复后仍记为映射冲突。
- 写入前冻结当前租户、唯一门店 ID/名称、源工作簿哈希、工作表、列位、目标行号和总数。
- 禁止把租户、门店、真实 SKU、Cookie、token、签名或用户工作簿写入 Skill 仓库。

## 2. 必须迁移的资料

每个源 SKU 在目标门店的当前快照至少包含并保持：

1. 渠道库存：按平台真实单位迁移，禁止把展示库存猜成可售库存。
2. 库位：原库位码原样迁移；若平台只有导表入口，只使用当前模板与当前门店 ID，导入后独立回读。
3. 供应商关系：供应商标识、采购关系和适用采购价按当前接口语义迁移；不能仅因页面显示供应商名称就认定成功。
4. 渠道状态：目标 SKU 最终必须保持用户要求的上架状态；门店商品与已上线渠道状态都要独立回读。

四类资料任一无法读取、写入或验证时，不得删除对应源 SKU。

库位导入按“同一门店、同一批次一个合并工作簿”组织，不为每个 SKU 生成单独文件。补偿重跑优先复用该合并工作簿；导入任务完成后必须下载失败明细，并按目标 SKU 证明其不在失败集合。

普通供应商导表若明确返回“请去网采中心创建”一类语义，不得反复重传普通导表。此时只为这些行加载网采分支：从当前成功页面确认 `sku-relations-query` reader 与 `/qnh-gw2/scm/online-procure/save-relation` writer 的真实 method、payload 和业务成功字段，保存供应商、采购价、单位、起订量、倍数、默认关系及网采商品链接/规格后再独立回读。历史端点只作发现线索，不能跳过当前页面确认。

## 3. 动作顺序与破坏性确认门

单行顺序固定为：

`读取源快照 -> 覆盖目标 SKU 到门店 -> 迁移库存/库位/供应商/渠道状态 -> 目标上架并回读 -> 删除确认门 -> 删除源商品及已上线渠道商品 -> 最终双向回读`

- 默认单热 writer；先做一条不含删除的 canary。
- 删除前必须展示唯一门店、准确待删源 SKU 数、canary 的四类资料与上架回读结果，并核对已有授权是否覆盖该集合及渠道删除影响；已覆盖时直接继续，超出范围时才请求确认。
- 未确认、确认范围不一致、canary 未闭环或删除对象不唯一时，删除数必须为 0。
- 删除结果未知时只回读，不盲目重发；目标商品未上架或资料残缺时不得继续删除下一条。

### SPU 级删除保护

- 如果删除 payload 使用 `storeSpuList` 或当前成功请求证明动作按 SPU 生效，必须在确认前用门店 reader 展开每个候选 SPU 的完整 `storeSkuList`。
- 只有 `storeSkuList` 的每个 SKU 都属于本次已确认源 SKU 集合时，才允许提交该 SPU。混合 SPU 整体剔除，禁止为了完成行数连带删除未确认规格。
- 混合 SPU 的确认行固定回填 `未完成：原商品删除（原SPU含未确认的其他规格）`；它不计入删除成功，也不能把目标商品存在冒充源商品已删除。

### 异步删除与剩余集重试

- `/api/product/store/batch-delete` 返回业务码 `300000000` 且文案为“任务处理中”时，只表示异步任务已受理，不表示任何一条已经删除。
- 每轮提交后按源 SKU 全量回读：不存在才计删除成功，仍存在则记录待核验剩余集。异步受理、观察窗口无进展或超时都不能证明原删除未执行；先查询原任务。只有原任务明确终止/失败且逐项确认未删除，或当前接口有已验证的幂等保障时，才可在原授权范围重提精确剩余 SPU。
- 最终必须同时证明：安全源 SKU 剩余数为 0、目标 SKU 全部存在、用户要求的渠道均上架。写响应、页面提示或任务列表完成都不能替代这三项回读。

## 4. 原生请求与证据

- `runtime_guided` 要求从当前登录页面的成功请求确认 endpoint、method、content-type、payload、业务成功字段和必需标识。
- 不读取 Cookie/localStorage，不绕过验证码或风控；会话或租户 fence 变化立即停止。
- 每类写入都要有独立 reader，不能用写响应或列表缓存代替。
- 批量放量只能在同一 manifest、同一门店、同一请求画像下进行；429/403/5xx 或语义漂移时降档并加载调试合同。

## 5. 固定工作簿结果 Schema

保留源工作簿所有工作表、行序、公式和样式，只写用户指定的结果列（缺省为 J 列）：

| 终态 | 结果列固定内容 |
|---|---|
| 源商品已删除、目标已上架、四类资料全部回读一致 | `原商品删除，新商品已上架，资料已迁移成功` |
| 尚未触发删除确认 | `待确认：原商品尚未删除` |
| 失败或部分完成 | `未完成：<最早未通过步骤>` |

失败步骤词只允许：`目标SKU不存在`、`目标覆盖门店`、`渠道库存迁移`、`库位迁移`、`供应商关系迁移`、`渠道状态迁移`、
`新商品上架`、`原商品删除`、`最终回读`、`映射冲突`。只有以下两个高风险原因允许追加固定括号说明：

- `未完成：原商品删除（原SPU含未确认的其他规格）`
- `未完成：映射冲突（E/H为同一SKU，商品已恢复并上架）`

未进入 manifest 的结果单元格必须保持原值；同一终态不得改写为其他近义句。

## 6. 完成门

- `成功数 + 待确认数 + 未完成数 = manifest 数`，且非目标行变化数为 0。
- 每条成功行都同时证明：源 SKU 在目标门店不存在、目标 SKU 存在且上架、库存/库位/供应商/渠道状态与源快照一致。
- 批量计数必须显式拆出：删除成功、混合 SPU 未删、映射冲突、资料迁移未完成、操作前已不存在等分项；风险标签可能重叠，不能相加。另按每行唯一最终状态对账，成功、待确认及未完成数合计等于 manifest。
- 工作簿公式变化数为 0，保存后独立重开；至少渲染一个成功样例和一个异常样例（若存在）。
- 只有全部完成门通过的行才能写成功固定句；批量结束后对 manifest 全量复扫，不能用抽样代替最终结论。
