## 1. 适用方式

本文件沉淀来源会话 `019fae58-ac52-7f11-918a-fc069cb65a5c` 的可复用、低敏经验。
新账号只复用规则、提示词来源、字段合同和脚本，不复用端口、profile、Cookie、tenant、store、SPU、
provider 任务号、图片 URL、上传回执、checkpoint 或 write intent。

每次新任务先读取实时页面、审核原文和当前项目正式实现。历史数字只说明规则为何存在，不能作为新账号现状。

## 2. 会话与账号硬绑定

任何列表读取、图片上传或商品保存前都生成并核对 `session_identity.json`，至少包含：

- 用户指定的 CDP 端口、实际 WebSocket 端点和 profile 目录。
- 当前页面 URL、route、tenant/store ID 与可见店铺名。
- 当前筛选 URL、筛选标签和登录状态。
- 本次独立 run-dir、manifest ID 与开始时间。

用户指定端口/店铺与实际身份任一不一致时，所有读数标记 `invalid_wrong_session`，上传和保存均为零发送。
不能用另一个 Chrome 的“不可售 400 条”回答当前账号，也不能因为两个页面标题相似就复用数据。
跨账号隔离要覆盖读取、上传、保存、provider claim 和审计，不只是 Cookie/profile。

用户没有要求原点账号时，不打开或登录原点操作台；CDP 直连治理只保留牵牛花首页和商品主档。

## 3. 清单、快照与集合口径

### 3.1 三个集合必须分开

每份报告同时维护：

- `platform_current_set`：当前筛选的全平台不可售 SPU。
- `initial_manifest_set`：本次冻结的原始目标 SPU。
- `task_new_set`：运行期间新进入不可售、但不在原始目标中的 SPU。

核心计算：

```text
still_unavailable_original = initial_manifest_set ∩ platform_current_set
exited_original = initial_manifest_set - platform_current_set
new_after_start = platform_current_set - initial_manifest_set
```

禁止只用“总数差”推断处理效果。总数下降 100 可能恰好是原队列退出 100，也可能同时发生退出与新增；
只有集合差能回答。截图数字、页面缓存数字和另一次冻结数字没有时间戳与集合哈希时不得互相相减。

### 3.2 冻结和稳定门

- 原始 Excel/CSV 若存在，复制到 run-dir，记录 SHA256，并设只读；保持原始行号、SPU 和范围。
- 分页 `page-size` 只用平台支持范围。total 在分页中变化时默认失败关闭。
- 动态复扫至少连续两次取得相同 SPU 集合哈希，才标记稳定；仅数量相同不够。
- 报告原始范围、平台总数、范围外交集和新增 SPU，避免把“349 中 344 属原表、5 条范围外”混成一个口径。

## 4. 报错到动作的闭环

逐 SPU 保存审核原文，允许一条商品命中多个原因。统计时同时输出 `primary_reason` 和 `all_reason_hits`；
原因类别会重叠，不能把各类命中数直接相加当商品总数。

每轮策略固定为：

```text
读取当前审核原文
→ 拆成字段/图片/监管/经营范围原因
→ 对每个原因选择唯一处理路由
→ 合并为单 SPU one-pass 计划
→ 保存并独立回读
→ 等待审核后逐原因比较
→ 同原因定位合同错误；新原因只建增量计划
```

高频路由：

| 原因族 | 默认动作 | 不得混淆 |
|---|---|---|
| 普通属性、标题、SKU | 官方建议或同 SPU 明文事实；缺口走博查字段合同 | 官方建议仍需字段对齐与规格冲突门 |
| 类目、品牌、店内分类 | 当前 tenant 实时推荐/选项 ID | 不复用历史“无品牌”或分类常量 |
| 配料/营养 | 同 SPU 真实标签优先；正式提示词清晰化后逐字核验 | `ready` 不代表配料、数值、GTIN 正确 |
| 包装标签、背签 | 同款真实标签或正式提示词；先做槽位审计 | 包装标签与背签是两个不同槽位 |
| 尺寸、纺织 | 当前包装/铭牌/吊牌的明确事实 | 型号数字不得当尺寸 |
| 3C、化妆品/医疗备案 | 权威登记或当前商品真实材料 | 不生图、不写固定编号 |
| 图片质量/数量 | 同 SPU 清晰图、精确同款图库；必要时主图正式美工流程 | 主图焕新不能替代专项图 |
| 禁售/经营范围 | 转人工 | 不通过改名、换图或猜类目规避 |

平台建议与当前值一致时记 `no_change`，继续处理同条审核中的其他缺口；不重复保存制造审核事件。

普通字段的已验证细则：

- 品牌自由文本可能保存成功却被归一化为空；只能使用当前 tenant 实时品牌库的真实选项 ID。
- 标题品牌拼写必须与包装逐字一致，包含大小写；同时删除图片不支持的医疗/功效词。
- 功率、型号优先取当前 SPU 包装/铭牌；只有用户明确允许且单档电压、电流均清晰时，才可按
  `W=V×A` 推导并在审计中标记推导。容量 mAh 永远不能当功率。
- 标题含互斥线索（充电/电池、单人/双人、罐/瓶等）时阻塞冲突字段；不受冲突影响的事实可单独写。
- 尺寸 OCR 必须有数值和单位边界并目视标注线；型号字符串中的数字不得进入尺寸。
- 标题补规格前先检查平台长度上限，删除重复营销词后保留核心品名与唯一 SKU 事实。
- 主图质量问题优先在同 SPU URL 集合内重排；保存前后集合必须相同，只允许顺序变化。

## 5. 专项图槽位合同

实测稳定映射如下；实际写入仍须同时核对实时 `pictureType + title + description + numLimit`：

| pictureType | 业务槽位 |
|---:|---|
| 3 | 包装标签/包装参数 |
| 4 | 3C/品质资质 |
| 5 | 配料与营养成分 |
| 6 | 纺织品使用说明 |
| 7 | 吊牌/洗唛 |
| 8 | 背签 |
| 13 | 尺寸图 |

不能只按中文近似词或历史 type 推断。曾有大量背签被写到 `type=3`：详情顶层看似存在图片，
但真正背签槽位 `type=8` 仍为空。每个批次先执行槽位审计：

1. 读取审核原文要求的业务图类型。
2. 读取当前槽位的 type、title、description、URL 集合和数量上限。
3. 查找同 SPU 已生成/已上传图片是否落在错误槽位。
4. 能确认同一制品时直接迁移/复用 URL，不重新生图、不重新上传。
5. 一个槽位有多张互补图时先合并最终 URL 集合，只保存一次。

审核明示缺图但详情漏槽位时，只有 Skill 已明确批准的最小兼容槽位可以构造；不得把尺寸/营养兼容
外推到 3C、备案、医疗、检验报告等法定槽位。

## 6. 图片生成、复用与错槽迁移

图片状态必须拆成：`candidate → provider_submitted → provider_ready → visual_accepted → uploaded →
qnh_saved → materialized → audit_exited`。任何前置状态都不能冒充后置状态。

生成前顺序固定：

1. 扫描同 SPU 主图、详情图和已有专项图。
2. 扫描当前账号图库的精确标题候选并做品牌、型号、规格、数量和图案冲突门。
3. 扫描是否已有同业务键 provider receipt 或已上传 URL。
4. 先修复错槽或复用真实图；只有确实缺制品才建立 provider job。
5. 新图片类型先给出 5 个代表 SPU 的图片、槽位和核验结果，再决定是否扩量。

重复“售后/提示”通用图不能凑主图数量；完整标题搜索命中也不能替代目视同款核验。现有旧生成图可能含
未经核验的厂商、许可证、条码等，不能反向作为真实标签证据。

主图焕新可以修复主体占比、水印、模糊等原因，但不能替代背签、配料营养、尺寸或 3C 专项图。
曾出现主图批量使大部分商品先退出，剩余商品仍全部报原专项图原因；必须按审核原因继续走正确槽位。

## 7. 保存物化的三面证据

图片/字段成功至少需要：

1. **请求面**：实际发出目标保存请求，HTTP 与业务码受理；保存前已持久化 write intent。
2. **数据面**：独立详情回读目标字段/完整 URL 集合与预期一致，非目标字段未被清空。
3. **页面面**：重新打开或刷新编辑页，正确槽位仍显示目标内容。

普通商品在请求面和数据面精确一致、且平台只做容器归一化时，可按既有兼容合同判物化；但出现
编辑页与详情不一致、关联美团医药标品库、页面提示不可编辑、或点击保存零请求时，页面面是强制门。

已验证假成功：详情顶层已有 URL，编辑页槽位为空；选图后临时可见，点击保存却零更新请求，刷新后消失。
此类必须标记 `standard_library_restricted/not_materialized`，不能计入完成数。

旧截图可能展示刷新前状态。复核时先重开编辑页；但“重开后可见”仍不能替代实际保存请求与独立回读。

## 8. 异步审核与纠错反馈

审核可能数分钟至 1–2 小时。批次效果以目标 cohort 计算，同时报告平台总量漂移：

- `target_exited_count / target_count`
- `target_same_reason_count`
- `target_new_reason_count`
- `platform_new_after_start_count`

例如 50 条全部上传、保存、回读后，10 分钟有 46 条退出、4 条仍报同一原因；正确动作是核对 4 条的槽位、
页面物化和制品内容，绝不能为这 4 条再次付费生成同一业务任务。

同原因仍在时按顺序自纠：

1. 当前字段或 URL 是否仍存在。
2. 写入的字段路径和 pictureType 是否正确。
3. 是否覆盖全部门店。
4. 编辑页刷新后是否仍可见、保存请求是否真实发送。
5. 制品是否完整满足审核文字，而不只是“有一张图”。
6. 审核是否仍是旧快照；用稳定双快照确认。

原原因消失、新原因出现时，只为新原因建增量计划。审核先退出后又因独立原因回流，不得重写已经物化字段。

## 9. Provider、OCR 与并发

- 业务 job 与 provider task 必须一一对应；一次 submit 后只 query 原任务，重复 submit 计数必须为 0。
- `provider_ready`、上传成功、QNH 保存成功、审核退出分别统计。
- 整批同步预校验必须早于任何付费协程；监管类违规任务标记 `validation_rejected/not_sent`。
- 已拿到 provider_task_id 后的 terminal failure、查询超时、制品拒绝或审核未退出都不自动重提。
- 字段/QNH 保存默认单热页；只有同量 canary 更快且资源余量持续通过才按不同 SPU `1→2→4` 扩量；同一 SPU 串行且 mutation 单飞。
- OCR/Tesseract 每账号最多 4 workers；同机多账号协调资源，优先串行。
- OCR 使用共享图片缓存、`OMP_THREAD_LIMIT=1` 和小分片落盘；40 SPU 长任务多次被 SIGTERM，
  应改为最多 10 SPU 分片，必要时单 SPU/workers=1。
- 不在扫描结束时才一次性写结果；每个分片/商品完成即持久化，恢复时复用缓存和 receipt。

## 10. 审计表与汇报口径

审计至少包含以下工作表或等价表：

- 原始范围与 SHA256。
- 平台当前全量、原始交集、运行期新增。
- 字段级事件：审核原文、字段、旧值、新值、证据、expected-old、保存和回读。
- 图片任务：pictureType、提示词版本、reference hash、provider submit/query/task_id、视觉结论、上传回执。
- 物化验证：请求面、数据面、页面面。
- 审核反馈：原原因、当前原因、退出/同因/新因。
- 阻塞项、性能、重复 submit/save 统计。

最终汇报必须分别给出：当前平台不可售、原始目标仍不可售、原始目标已退出、运行期新增、保存回读成功、
审核退出、同因残留、监管/材料阻塞。不要用“写了多少字段”回答“还剩多少不可售”。

## 11. 已验证反例

- 连到错误 CDP 后得到的列表总数与目标 manifest 零交集；虽然未写入，但此前统计全部无效。
- 背签写入包装标签 `type=3`，顶层接口有图，实际 `type=8` 仍空；必须错槽迁移。
- 页面选择图片后没有任何更新请求，刷新即消失；点击保存不等于保存发生。
- 同一 SPU 的多张互补图被拆成连续变更，旧校验器拿中间集合对最终集合误报失败；应先合并最终集合。
- 生成图清晰但把 25cm 写成 25mm；必须在上传前拦截，且不为换图自动二次付费。
- 图库完整标题命中不同品牌/型号/规格；查询结果不是证据。
- 批量主图焕新短时出队，随后因背签、营养、3C 等独立原因回流；主图不能替代专项材料。
- 已有专项图或旧生成图不代表审核必需内容完整；“槽位非空”和“审核通过”是两件事。
