# 统一业务成功合同 v1

本合同统一“商品治理何时算业务成功”，不统一平台协议。牵牛花、美团、翱象、淘宝闪购的身份、请求、签名、
payload、reader、planner、writer、回读器、审核集合和失败码始终由各自适配器拥有；共享核心禁止解释原始平台响应，
也禁止一个平台借用另一个平台的成功判断。

## 1. 共同证据模型

每个目标商品必须由平台适配器输出同一组低敏、平台无关事实：

- `target_identity`：平台、租户/门店、商品键、任务模式、run、页面/会话 fence；
- `baseline`：写前问题、目标字段或图片槽位、非目标字段与媒体摘要、适用审核集合；
- `plan`：证据来源、期望旧值、目标值或人工材料阻塞，不包含密钥、Cookie、签名或完整受保护请求；
- `mutation`：未发送、已发送、已受理、明确失败或结果未知；
- `materialized_readback`：由独立于保存响应的正式 reader 重新取得的最终值、结构与保护摘要；
- `scope_rescan`：任务模式要求的不可售、审核、违规、影响流量或其他平台集合复扫；
- `terminal_state`：下述统一终态之一，并保留平台原始低敏 reason 的映射。

保存 HTTP 2xx、业务 code=0、上传成功、页面不再红框、provider 完成或计划已生成都只能作为阶段事件，不能直接产生
业务成功终态。

## 2. 统一终态

- `verified_complete`：目标值已物化，最终结构正确，非目标保护通过，且适用范围复扫通过；
- `verified_no_change`：写前已满足合同，独立终读再次证明无需修改；
- `missing_on_platform`：平台正式 reader 明确证明目标不存在，单列且不计入平台现存完成率分母；
- `waiting_platform_review`：字段已物化但平台审核集合尚未退出，不得计为清退成功；
- `manual_evidence_required`：缺少真实监管/商品材料，禁止伪造，继续处理其他商品但本商品不计成功；
- `pending_verify`：保存结果未知、身份变化或回读暂不可得；只允许回读原写入，不自动重发；
- `blocked`：平台能力未实现、身份冲突、结构未知、验证失败或安全门关闭；
- `failed`：已有明确且不可由当前合同自动恢复的失败证据。

只有 `verified_complete` 与 `verified_no_change` 计入平台现存商品的业务完成数。`missing_on_platform` 只完成清单归档，
不计作已治理商品；其余终态均不得通过换统计口径冒充成功。

## 3. 商品信息填充共同完成门

平台现存商品只有同时满足以下条件才算信息填充成功：

1. 当前任务范围内全部必填、无效和平台明确报错字段均有合法值，类型、候选 ID、复合结构和字段间语义一致；
2. 保存后由正式独立 reader 重新读取，逐目标字段与计划一致；无修改商品也完成终读；
3. 原主图、详情图、既有资质图、非目标字段、SKU 结构和其他受保护事实没有被删除、缩短、重排或串改；
4. 不存在未处理的目标字段、回读不一致、未知写结果或本轮新增问题；
5. 全量现存目标重新验证，结构问题为 0。抽样、请求成功率、保存数或本轮修改数不能推断 100%。

各平台可以使用不同字段模型和 validator，但必须把结果映射到这五个共同事实。平台适配器没有实现其中任一证据时，
对应能力继续 `planned` 或失败关闭。

## 4. 资质图共同完成门

资质图成功除满足身份、写回、独立回读和非目标保护外，还必须证明：槽位/类型精确、图片已物化、内容与商品事实一致，
且法定证照、备案、注册、许可、检验报告、公章及 3C/CCC 等来自真实可核验材料。生成图、普通主图或相似商品材料
不得冒充法定证据。缺真实材料固定进入 `manual_evidence_required`。

上传成功不等于槽位写回成功；槽位写回成功也不等于审核退出。两者必须分别统计。

## 5. 不可售与清退配额共同完成门

不可售治理先冻结原始候选池、用户要求治理的集合与目标数。用户说“处理 N 条/清除 N 条”时，N 固定为最终核验成功
配额，不是尝试数、计划数、provider 数、保存数或已物化数。可以在冻结候选池内按平台适配器规则补选后续商品，
但不得把池外商品静默加入任务。

计入 `verified_cleared` 的商品必须同时满足：

- 已达到本合同第 3 或第 4 节适用的物化与保护门；
- 已退出任务冻结时要求治理的不可售、审核失败、违规删除/下架和影响流量集合；
- 本轮没有让商品新进入任何保护性问题集合；
- 平台适配器完成稳定复扫；异步审核中的旧快照固定为 `waiting_platform_review`。

报告固定区分 `processed`、`mutation_accepted`、`materialized`、`waiting_platform_review`、
`verified_cleared` 与 `verified_target`。只有 `verified_cleared >= verified_target`，或冻结候选池已耗尽并如实报告残余
终态，任务才能结束；后者是部分完成/阻塞，不得宣称完成配额。

## 6. 恢复、重试与并发

- 登录过期、验证码或浏览器被迫退出时保留 run、manifest、checkpoint、write intent 与任务 ID；恢复同一身份后续跑；
- 只读失败可按当前平台合同有界重试；已发送、已受理或结果未知的 final save 必须先独立回读，禁止盲目重发；
- 已接单 provider 任务只 query 原任务，除非项目最高级合同明确批准再次付费提交；
- 并发只发生在平台适配器证明相互独立的商品执行上下文之间；同一商品的读、期望旧值校验、保存和回读始终串行；
- 大任务可以分闭环波次，但每波必须完成规划、写回、独立回读、范围复扫和 residual，再进入下一波。

## 7. 审计与交付

所有平台把上述证据映射到 `product-governance-operations-workbook-v1`。执行汇总必须从最终商品终态重新计算，
不得复用旧批次数字。工作簿通过 Schema validator 只代表结构正确；仍须通过当前平台完成门和同一 execution run 的
handoff gate，才能向用户交付并宣称完成。
